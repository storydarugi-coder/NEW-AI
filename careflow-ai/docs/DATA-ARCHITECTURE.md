# CareFlow AI 데이터 아키텍처 및 보안 원칙

## 1. 데이터 흐름 다이어그램

```
┌─────────────┐     ┌──────────────────┐     ┌──────────────────────┐
│  EMR/차트    │     │  연동/정제 계층    │     │  CareFlow 운영 DB     │
│  (병원 내부)  │────▶│  (ETL Pipeline)   │────▶│  (최소 데이터만 저장)  │
└─────────────┘     └──────────────────┘     └──────────────────────┘
                           │                          │
                    ┌──────┴──────┐             ┌─────┴─────┐
                    │ 버리는 필드:  │             │ 저장 필드:  │
                    │ · 차트 원문   │             │ · 차트번호  │
                    │ · 자유서술    │             │ · 성별     │
                    │ · 주민번호    │             │ · 출생연도  │
                    │ · 주소       │             │ · 진료코드  │
                    │ · 보험번호    │             │ · 진단코드  │
                    │ · 상세 진료기록│             │ · 치아번호  │
                    └─────────────┘             │ · 방문일   │
                                               │ · 유입경로  │
                                               └───────────┘
```

## 2. PII 분리 아키텍처

```
┌─────────────────────────────────┐
│         Patient (운영 데이터)      │
│  · id (internal key)            │
│  · chartNumber                  │
│  · gender, birthYear            │
│  · isVip, tags                  │
│  · 식별 불가 — 운영 목적만        │
└────────────┬────────────────────┘
             │ 1:1 (분리 저장)
┌────────────▼────────────────────┐
│     PatientIdentity (PII)       │
│  · name (이름)                  │
│  · phone (전화번호)             │
│  · 최소 권한 사용자만 접근       │
│  · UI에서 기본 마스킹 표시       │
└─────────────────────────────────┘
```

### 왜 분리하는가?
- **운영 엔진(리콜 탐지, 우선순위 계산)은 PII가 불필요**: 방문일, 진료코드, 진단코드만으로 동작
- **메시지 생성 시에만 이름 필요**: 마스킹된 이름으로도 생성 가능
- **향후 권한 체계 적용 시**: PatientIdentity 테이블에 별도 접근 제어 가능
- **데이터 유출 시 피해 최소화**: 운영 DB만 유출되면 개인 식별 불가

## 3. 저장되는 필드 / 저장하지 않는 필드

### 저장 (운영에 필요한 최소 필드)

| 테이블 | 필드 | 목적 |
|--------|------|------|
| Patient | chartNumber | 차트 식별 (EMR 연동 키) |
| Patient | gender | 리콜/메시지 개인화 |
| Patient | birthYear | 연령대 기반 추천 |
| Patient | isVip | 우선순위 계산 |
| Patient | tags | 정형화된 운영 태그 (자유 텍스트 아님) |
| PatientIdentity | name | PII: 마스킹 대상 |
| PatientIdentity | phone | PII: 마스킹 대상 |
| Visit | visitDate | 리콜 주기 계산의 핵심 |
| Visit | channel | 유입 경로 분석 |
| Visit | isCta | CTA 귀속 판단 |
| Procedure | code, name | 치료 중단 탐지 (정형화된 코드만) |
| Diagnosis | code, name | 잠재 수요 탐지 (정형화된 코드만) |

### 저장하지 않음 (데이터 최소화)

| 데이터 유형 | 이유 |
|------------|------|
| 차트 원문 (자유서술) | 운영 판단에 불필요, 민감정보 포함 가능 |
| 주민등록번호 | 법적 보관 의무가 아닌 한 저장 금지 |
| 주소 | 리콜/메시지에 불필요 |
| 보험 상세 | 운영 목적 외 |
| 진료 상세 기술 | 코드화된 정보로 충분 |
| 방사선/영상 | 운영 DB에 저장 불필요 |
| 동의서/서약서 | 별도 문서 관리 시스템 |

## 4. EMR 연동 시 변환 명세

### 현재 (데모/Mock)
```
SeedData → Patient + PatientIdentity + Visit + Procedure + Diagnosis
```

### 향후 (실제 EMR 연동)
```
EMR API/HL7/FHIR
  → ETL Pipeline (정제 계층)
    → 코드 매핑 (진료코드 표준화)
    → 자유텍스트 → 정형 태그 변환 (LLM 또는 규칙)
    → PII 분리 (이름/연락처 → PatientIdentity)
    → 불필요 필드 폐기
  → CareFlow 운영 DB
```

### 자유입력 텍스트 처리 방침
- **차트 메모**: 정형화된 태그로 변환 후 `Patient.tags`에 저장 (예: "야근잦음,예약취소이력")
- **진료 기록**: 진료코드(수가코드)와 진단코드(KCD)만 추출, 원문은 저장하지 않음
- **방문 메모**: 운영에 필요한 최소 정보만 요약 저장

## 5. LLM/메시지 생성 안전성

### 원칙
- 외부 AI API(Vertex AI 등)에 **차트 원문 전체를 보내지 않음**
- 메시지 생성에는 **최소 컨텍스트만 사용**:
  - 마스킹된 이름 (김*수)
  - 리콜 사유 (정형화된 텍스트)
  - 마지막 방문일
  - 톤/길이 설정

### 구현
```typescript
// src/lib/privacy.ts - sanitizeForLLM()
{
  patientName: maskName("김민수"),  // → "김*수"
  reason: "신경치료 시작 후 14일 이상 미내원",
  subType: "nerve_treatment",
  recentVisitDate: "2026-01-15"
}
```

### 로깅 원칙
- `AuditLog`에 액션 기록 시 PII 포함 금지
- `entityType` + `entityId`로만 참조
- 에러 로그에 환자 정보 노출 방지 (`console.error`에 patient 객체 전체 출력 금지)

## 6. 보안/감사 기능

### AuditLog 테이블
- 접속 기록: `view_pii` (PII 조회 시)
- 변경 기록: `update_status`, `review_attribution`
- 발송 기록: `generate_message`
- 데이터 작업: `seed_data`, `export_data`

### 환경변수 분리
- `DATABASE_URL`: DB 연결 (Vercel 환경변수)
- `VERTEX_AI_*`: AI 서비스 인증 (별도 비밀키)
- `.env` 파일은 `.gitignore`에 포함

### 향후 운영 시 주의사항
1. **HTTPS 필수**: 운영 환경에서 HTTP 사용 금지
2. **인증/인가**: 현재 데모는 인증 없음 → 운영 시 NextAuth 등 도입 필요
3. **DB 암호화**: PatientIdentity 필드 암호화 저장 권장
4. **접근 로그**: 모든 PII 조회를 AuditLog에 기록
5. **데이터 보존 기간**: 운영 정책에 따른 자동 삭제/아카이브
6. **백업 암호화**: DB 백업 시 암호화 필수

## 7. 개인정보를 최소화하면서도 핵심 기능이 가능한 이유

| 기능 | 필요 데이터 | PII 필요 여부 |
|------|-----------|-------------|
| 치료 중단 탐지 | 방문일 + 진료코드 | 불필요 |
| 스케일링 리콜 | 마지막 스케일링일 | 불필요 |
| 임플란트 점검 | 시술일 + 진료코드 | 불필요 |
| 잠재 수요 발굴 | 진단코드 + 방문일 | 불필요 |
| 우선순위 계산 | 탐지 결과 + VIP여부 + 방문 빈도 | 불필요 |
| CTA 광고 귀속 | 유입 채널 + 방문일 + 캠페인 | 불필요 |
| 메시지 생성 | 마스킹된 이름 + 사유 | 이름만 (마스킹 가능) |
| 메시지 발송 | 이름 + 전화번호 | 발송 시점에만 접근 |

→ **엔진 동작, 광고 귀속 추적, 정산 계산은 모두 PII 없이 가능**
→ **PII는 UI 표시와 메시지 발송 시점에만 필요** → PatientIdentity 분리가 합리적
